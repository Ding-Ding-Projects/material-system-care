# Minecraft server creation and management

Status: **unimplemented**. This article records the required installed-application capability, not verified server support. The fixed inventory contains a separate incomplete row for each of the 28 desktop surfaces. The static public website documents the manager; an optional authenticated local bridge may expose real capabilities, but a browser page cannot own local processes, SSH credentials or a Docker daemon. Its existing website requirements remain unchanged.

## Workflows and execution targets

The installed suite must provide guided creation and explicit adoption, distribution/flavour installation, custom plugin/mod/pack management, version switching, compatible runtime provisioning, start/graceful stop/restart, scheduling, health and resource monitoring, logs, worlds and dimensions, import/export, backups and restore, upgrades and rollback, players, operators, allowlists, bans, permissions, network/listening configuration, typed rules and supported commands. The four independent adapters are a local Windows process, local Docker container, SSH process and SSH Docker container. Each action binds exact host, process or container, paths, ports, distribution digest, permissions and capacity. Discovery alone does not authorize adoption or termination.

## Version discovery and rich controls

Discover complete Java and Bedrock release histories and applicable development channels through authoritative paginated catalogues, recording immutable identities, retrieval time, stale/offline state and unavailable distributions. A client-only release is not a server distribution. Resolve runtime, architecture, configuration, command and extension compatibility for the selected version; sampled execution never proves every discovered version.

Boolean properties use switches, enumerations use searchable selectors, bounded numbers provide units and keyboard alternatives, names have validated clearable fields, collections have structured transactional editors, identity and permission lists use real target records, and schedules include time zones and missed-run behavior. Every descriptor needs a stable identifier, authoritative source, edition/version/flavour, type and bounds, default, restart semantics, contextual help, permission, persistence and an actual consumer. Unknown fields are preserved without pretending unsupported extensions have rich controls.

## Failure, recovery and privacy

Connection loss differs from a stopped server. Cancellation and partial outcomes remain explicit. Restore and rollback must validate source identity, destination, ownership and exact bytes. Credentials use protected local storage and are excluded from logs, exports and captures. A server restart acts only on the selected owned server, never the local host power state. Acceptance uses disposable owned servers and worlds; unrelated targets are not modified.

## Verification

Maintain edition × version × flavour × target × extension rows with separate source, implementation, installation, runtime, GUI, layout and evidence verdicts. Exercise creation, adoption, configuration readback, lifecycle, permissions, extension installation, world operations, backup/restore, upgrade/rollback, cancellation, reconnect and invalid inputs. Retain actual built interactions and captures with source and artifact hashes. Missing historical distributions, credentials, target infrastructure or unrun acceptance remain gaps.

The structural coverage test deliberately rejects missing feature rows, desktop requirements, a changed application scope and a fabricated website-owned server requirement. It does not execute a server or establish implementation.
