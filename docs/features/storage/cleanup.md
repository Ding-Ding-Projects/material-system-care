# Temporary-file plans and recovery

1. Call `cleanup.scan` with `{ "minimumAgeDays": 7, "maxEntries": 10000, "maxHashMiB": 512 }`. Only the current user's `%LOCALAPPDATA%\\Temp` is eligible, and only if it agrees with the operating-system temporary path. A supplied `path` must match that root exactly. The minimum age is 1 through 365 days. The result includes `planId`, exact targets, total bytes, traversal counters, expiration and `mutationPerformed: false`.
2. Select targets in the displayed plan and review their exact paths. Call `cleanup.apply` with `{ "planId": "32-hex-character-id", "targetIndexes": [0, 2], "confirmed": true }`. Indices refer to the original server-returned `targets` array, not a filtered or sorted display. Missing or empty selection is rejected, as are duplicates, non-integers and out-of-range indices. Earlier clients that omit selection must be updated; omission never silently means the full plan.
3. Use `cleanup.history` with `{}` to retrieve persisted recovery receipts. Call `cleanup.restore` with `{ "receiptId": "32-hex-character-id", "confirmed": true }` to restore the receipt's files.

Plans are created once, expire after one day, and hold at most 1,000 files. Each records file identity, length, UTC creation and modification ticks, SHA-256, the approved root and minimum age. Apply rechecks scope, every ancestor, identity, timestamps, age and complete content before moving. Reparse points and hard links are excluded. Recovery storage itself is excluded from scanning. The service does not accept arbitrary cleanup paths, document roots, disk commands, or permanent deletion.

Cleanup and restore use a Windows file handle with delete access and sharing that excludes writers and deletion. The rename is performed through that same verified handle to an absolute destination with replacement disabled. Every destination ancestor is held open without delete sharing and its final handle path is verified before the rename, preventing ancestor replacement while the move runs. Recovery must be on the same volume as the temporary directory. A cross-volume move fails safely and retains the source rather than performing a non-atomic copy/delete operation.

Each receipt is journaled before a move and updated through an atomic replace after the move. Cancellation leaves completed moves in recovery and reports a partial result. `pending` or `restoring` states can remain if the process ends between the rename and journal update. If a `restoring` record has no recovery file but the original path exists, restore opens that original file without write/delete sharing and revalidates its full identity, size, creation/modification timestamps and SHA-256. Only an exact match reconciles to `restored` with `INTERRUPTED_RESTORE_RECONCILED`. A different occupant remains a conflict even if its bytes and timestamps match. Other missing recovery files become `unresolved`; they are not claimed restored. Restore checks recovery identity and content before moving and never overwrites an occupied original path. Conflicts retain recovery bytes and their evidence for another restore attempt. Missing parent directories are not recreated automatically. A repeated apply with the same canonical selection returns the existing receipt without moving any file again. A different selection is rejected with SELECTION_CHANGED; scan again for remaining files. Legacy receipts represent the previous full-plan selection. Interrupted or canceled plans are not resumed by replay, and replay cancellation state is not historical cancellation provenance.

Apply returns `receiptId`, `items`, `plannedCount` (selected targets), `totalPlanCount`, `partial`, `cancelled` and `permanentDeletion: false`. Each item carries its original target, quarantine path, state and a stable reason when skipped or conflicted. Restore returns `receiptId`, `items`, `partial` and `cancelled`. History returns up to 1,000 receipts. General history records counts and receipt IDs, rather than file contents. Recovery records contain local paths and hashes and should be treated as private local data.

`SELECTION_REQUIRED`, `INVALID_SELECTION`, `SELECTION_CHANGED`, `CONFIRMATION_REQUIRED`, `SCOPE_NOT_ALLOWED`, `PLAN_EXPIRED`, `TARGET_CHANGED`, `HARDLINK_NOT_ALLOWED`, `REPARSE_NOT_ALLOWED`, `RESTORE_CONFLICT`, `RECOVERY_CHANGED`, `TEMP_ROOT_UNAVAILABLE` and `PLATFORM_UNSUPPORTED` describe specific refusal conditions. File access or rename failures retain bytes and yield `FILE_UNAVAILABLE` within the receipt. A malformed record yields `INVALID_PLAN`.

The internal fixture constructor can supply a sandbox temporary root to the compiled fixture executable. It is not exposed through IPC; fixture scan results carry `fixture: true`. Production constructs the module without that constructor argument.
